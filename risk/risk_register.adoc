= Risk Register
:toc:

[cols="1,3,2,2,3",options="header"]
|===
|ID |Risk |Likelihood |Impact |Mitigation / treatment
|R-001
|If authorization rules for citizens, KRA staff, Estonian Defence Forces staff, or delegated access are more complex than expected, then the chosen access-control model may not support the required workflows safely.
|High
|High
|Create a role/permission matrix for representative workflows and implement an authorization PoC. Test allowed and denied cases, including revoked or prohibited delegated access.

|R-002
|If the available TIS interface, access rules, or test environment differ from our assumptions, then the health-related workflow may require major integration or architecture changes.
|High
|High
|Validate the TIS integration early with a connectivity/API PoC using available documentation, sandbox access, or representative mocks. Record unsupported assumptions and adjust the integration boundary before detailed implementation.

|R-003
|If KVKR or Estonian Defence Forces systems do not provide suitable machine-to-machine interfaces for the required workflows, then the planned portal functionality may be impossible or significantly more complex to implement.
|High
|High
|Verify the required operations and data exchanges against available interfaces. Build a small PoC integration for one representative workflow and identify where adapters, asynchronous processing, or scope changes are needed.

|R-004
|If the portal stores data that should remain authoritative in KVKR, TIS, or Estonian Defence Forces systems, then duplicated or stale sensitive data may force later redesign and create privacy risks.
|High
|High
|Define the data owner for each major data category and prototype one representative workflow using the proposed ownership boundary. Review which data is stored, cached temporarily, or fetched on demand.

|R-005
|If the portal's integration with the State Authentication Service (TARA) does not behave as expected for supported eID methods, session handling, or authentication failures, then citizens may be unable to authenticate or sessions may be handled incorrectly.
|Medium
|High
|Integrate an authentication PoC with the TARA demo environment using OIDC. Test ID-card, Mobile-ID, and Smart-ID authentication where available, together with failed authentication, session expiry, logout, and TARA unavailability. Adjust the authentication and session design based on the results.

|R-006
|If a workflow spanning the portal and external systems partially succeeds, then requests may be lost, duplicated, or shown with an incorrect state.
|High
|High
|Implement a representative multi-system workflow and inject failures at different steps. Test retries and duplicate submissions, then adjust the workflow until accepted requests are not lost or processed twice.

|R-007
|If TIS, KVKR, or Estonian Defence Forces interfaces change during development or later maintenance, then an integration may break or force unrelated portal changes.
|High
|Medium
|Add contract and regression tests for each external interface. Simulate a compatible and a breaking interface change and verify that changes remain isolated to the affected integration.

|R-008
|If audit and privacy requirements are discovered too late, then important actions may not contain enough context for traceability or the architecture may collect more sensitive data than necessary.
|Medium
|High
|Prototype audit events for representative citizen and staff workflows. Review the recorded fields against security/privacy requirements and run tests that verify required events exist without logging unnecessary sensitive data.

|R-009
|If normal and peak workload assumptions are too low, then the chosen architecture may fail to meet performance and availability targets during conscription call-up or reserve-service peaks.
|Medium
|High
|Establish a baseline workload and run load tests at normal and five-times-normal load. Measure latency, error rate, throughput, and resource use; identify bottlenecks and revise the architecture where targets are missed.

|R-010
|If realistic external-system test environments or representative test data are unavailable, then integration behavior may remain unverified until late in the project.
|Medium
|Medium
|Request test access early and define representative interface mocks for unavailable systems. Run the same contract tests against mocks and real test environments when access becomes available, and resolve any differences before release.

|R-011
|If the Backend Application, as the only container with access to the Portal Database, Document Store, and Audit Store (ADR-0002), is compromised or misconfigured, then application data and documents could be exposed and false or missing audit events could go undetected.
|Low
|High
|Use separate credentials per store with least privilege, and give the Backend Application append-only access to the Audit Store. Evaluate audit integrity protection (e.g. hash chaining) in the Phase 3 audit-event prototype and test that the Backend Application cannot modify or delete existing audit events.

|R-012
|If a KVKR case reference is linked to the wrong portal request, for example after KRA replaces a reference or after a retried forward, then a citizen may see another person's case status or documents and their own request may appear lost.
|Low
|High
|Change the mapping only from a KVKR response that carries the same Request ID and the same person as the request's owner; otherwise keep the old mapping and alert helpdesk staff. Keep a history of earlier references. In Phase 2, test a reference replacement and a mismatched response against the KVKR mock and check that no request changes owner (see link:../docs/identity_model.adoc[identity model]).

|R-013
|If the personal identification code (the TARA subject) is used as an identifier in URLs, logs, audit events, or notifications, then personal data is exposed to parties who should not see it, and other people's identifiers become guessable.
|Medium
|High
|Use only the random Citizen ID and Request ID in portal interfaces, logs, and audit events, and send the personal identification code only to KVKR and TIS through the Integration Service. Add an automated check in Phase 2 that scans API paths, logs, audit events, and notification texts from a test run for the personal-identification-code pattern and fails if any is found.

|R-014
|If a delegation is copied into the delegate's session, a token, or a cache, then a revoked or expired delegation may keep working until that copy expires, and the delegate can still view the citizen's requests after the citizen has withdrawn consent.
|Medium
|High
|Read the delegation from the Portal Database on every request and never copy it into sessions or tokens. Test: a delegate views the grantor's request status; the grantor revokes the delegation; the delegate repeats the same request in the *same session* and must be denied, with a denied audit event. Repeat with a delegation whose end date has passed (see link:../docs/access_control_matrix.adoc[access control matrix]).

|R-015
|If an endpoint loads a request by its Request ID without checking the owner or a delegation, then a signed-in citizen can open another citizen's request by changing the Request ID in the URL.
|Medium
|High
|Put the ownership and delegation check in one shared authorization step in the Backend Application that runs before any request data is read, instead of repeating it in each endpoint. Test: for every endpoint that takes a Request ID, sign in as citizen A and call it with citizen B's Request ID. Each call must return the same response as a non-existent ID, return no data, and create a denied audit event. Run this automatically for every new endpoint.

|R-016
|If a forward of an old revision reaches KVKR after the citizen has taken the request back - for example because a forward whose reply was lost is still being processed when the portal asks KVKR "is there a case?" - then KRA may process content the citizen has withdrawn, or hold two versions of the same request.
|Medium
|High
|_Refined in Week 10 from the failure timeline in link:../docs/architecture.adoc#_failure_timeline_late_acceptance_of_an_old_revision[architecture.adoc]:_ a "no case" answer is not reliable while a forward may still be in flight. Design: every forward and answer carries the Request ID and revision; the Backend Application applies results only by compare-and-set on (Request ID, revision, expected status); a take-back of a request whose forward has an unknown outcome is refused until the settle window (2 × KVKR's maximum processing time) has passed and a KVKR lookup has answered (INV-2 in link:../docs/security_invariants.adoc[security invariants]). Test: KVKR mock processes a forward 50 s late and drops the reply; take back at 40 s - expect `409 TAKE_BACK_NOT_ALLOWED`; after the window the request becomes Forwarded for revision 1 without a second forward; after release and resubmission KVKR holds exactly one case with revision 2.

|R-017
|If take-back and resubmission can be repeated without limits, then a citizen or an attacker with a stolen session can create repeated load on TIS, KVKR, and KRA staff, or keep a request out of KRA's hands to delay a process.
|Medium
|Medium
|Limit take-backs to 3 per request, expire taken-back requests after 30 days, rate-limit state-changing calls, and alert on unusual take-back counts (ADR-0005, link:../docs/api_security_review.adoc[API security review]). Test: the fourth take-back returns `TAKE_BACK_LIMIT_REACHED` and makes no KVKR or TIS call.

|R-018
|If a state change is committed in the Portal Database but its audit event is not written to the Audit Store - because the Audit Store is unavailable or the Backend Application stops between the two writes - or if a duplicated message writes the event twice, then the audit trail no longer matches what happened to the request (SG-005, QA-003).
|Medium
|High
|Write each state change and an outbox entry in the same Portal Database transaction; an audit relay copies outbox entries to the Audit Store, which rejects a second event with the same event ID (Request ID, revision, transition); a compare-and-set that changes nothing writes no outbox entry. Alert if an event is not stored within 5 seconds (INV-3 in link:../docs/security_invariants.adoc[security invariants]). Test: make the Audit Store unavailable during a submission, deliver a KVKR release answer twice, and stop the relay between writing and marking an entry sent; expect exactly one event per state change and an alert after 5 seconds.
|===
