= Quality Attributes

== Prioritized quality attributes

[cols="1,2,1,1,4",options="header"]
|===
|ID |Quality attribute |Priority |Architecture-critical |Requirement

|QA-001
|Security & Privacy
|High
|Yes
|Protected health, defence-obligation, case, and document data must only be accessible to authenticated users with the required authorization. Unauthorized-access test cases must not return protected data.
|QA-002
|Availability
|High
|Yes
|The citizen-facing portal has an initial availability target of 99.9% per month, excluding planned maintenance. Failure of KVKR, TIS, or a Defence Forces system must not make unrelated portal workflows unavailable.

|QA-003
|Auditability
|High
|Yes
|All defined security-relevant actions must create an audit record containing the actor, action, affected resource, timestamp, and outcome within 5 seconds of the action.

|QA-004
|Interoperability
|High
|Yes
|The required exchanges with KVKR, TIS, and Defence Forces systems must pass integration/contract tests against every supported interface version.

|QA-005
|Performance
|Medium
|No
|Under normal load, 95% of portal-owned interactive requests must complete within 2 seconds. Operations waiting on an unavailable external system must return an explicit unavailable or pending state within 5 seconds.

|QA-006
|Usability
|Medium
|No
|At least 90% of representative test users should be able to view their case status, locate a summons or decision, and submit a requested document without help.

|QA-007
|Reliability & Fault Tolerance
|High
|Yes
|In defined external-system failure tests, no accepted request may be lost or processed more than once, and unrelated workflows must remain usable.

|QA-008
|Maintainability
|High
|No
|A compatible or breaking change to one external integration should require changes only to that integration and directly dependent portal functionality. Unrelated integration contracts must continue to pass their regression tests.

|QA-009
|Transparency
|Medium
|No
|All audit events classified as visible to the citizen must become accessible to the affected citizen within 24 hours and identify at least the accessing organization, time, and type of action.

|QA-010
|Regulatory Compliance
|High
|No
|The portal must comply with applicable EU and Estonian requirements for personal and health data, digital identity, data retention, information security, and national-defence services. Relevant requirements must be identified and verified for each supported service.

|QA-011
|Scalability
|Medium
|No
|When load increases from normal to five times normal, the system must be able to increase processing capacity while keeping peak-load response-time and error-rate targets within acceptable limits. Normal and peak workload baselines are still to be established.

|QA-012
|Cost Constraints
|Medium
|No
|Infrastructure usage and operational cost must be measurable per environment and attributable to the portal's major components and external integrations.

== Trade-offs

=== Security and privacy vs. usability and performance

Security and privacy take priority for access to health, defence-obligation, case, and document data, even when additional checks add latency or user steps.

=== Availability and reliability vs. cost

Critical citizen workflows require stronger failure isolation and redundancy. Additional resilience must be justified against its infrastructure and operational cost.

=== Auditability and transparency vs. privacy

Audit records must contain enough information to reconstruct important actions, while information exposed to citizens for transparency must not reveal protected internal or third-party information.

=== Interoperability and maintainability vs. performance

Isolation between KVKR, TIS, and Defence Forces integrations may add processing overhead, but changes to one external system should not unnecessarily affect the others.
