= Ownership Sketch

The following are initial ownership assumptions, aligned with the containers in the C4 container view (link:architecture.adoc#_4_containers[architecture.adoc, section 4]) and the data ownership decision in link:../adrs/ADR-0002-data-ownership.adoc[ADR-0002].

== Portal containers

[cols="2,4,3",options="header"]
|===
|Container |Responsibility |Ownership assumption

|Web Application
|User interface, service catalogue, profile, case/status presentation, document interaction.
|Citizen Services Portal team.

|Backend Application
|Identity and access (TARA integration, sessions, authorization, permitted delegation), case/workflow coordination, document handling and signing coordination, notification initiation, and audit event creation.
|Citizen Services Portal team. The identity and access and audit parts are reviewed by the portal security team.

|Integration Service
|Communication with KVKR, TIS, and Estonian Defence Forces Systems; isolates external interface differences from the rest of the portal.
|Portal integration team. Each adapter has a named contact person in the external organization.

|Portal Database
|Portal-owned application data (preferences, workflow state, notification metadata, configuration).
|Citizen Services Portal team; operated by the platform team.

|Document Store
|Uploaded documents until delivery or retention expiry.
|Citizen Services Portal team; operated by the platform team. Retention rules agreed with the receiving organizations.

|Audit Store
|Append-only audit events and transparency information.
|Portal security team. Administrators of the Portal Database do not have write access to the Audit Store.
|===

== Changes from the earlier sketch

The earlier sketch listed six logical services: citizen-facing portal, case/workflow handling, identity and access, external-system integrations, audit and transparency, and notifications. In the container view they map as follows:

* *Citizen-facing portal* became the Web Application.
* *Case/workflow handling, identity and access, and notifications* are logical responsibilities inside the Backend Application rather than separate containers. Splitting them is deferred until boundaries are validated (see ADR-0002, alternatives).
* *External-system integrations* became the Integration Service.
* *Audit and transparency* is split between the Backend Application (creating events and filtering views) and the Audit Store (storage).
