=== Tampering

Organisatsioonide vahel X-tee kasutusel. Eeldame, et X-tee säilitab terviklikuse. Kas turvaperimeetri sees on vaja servicite vahel hoida turvalist suhtlust?  Tähtis, et administraatorid ei saaks/ei teeks muudatusi audit logile, jälgida kellele see ligipääs. Vaja ka muretseda selle eest, et kõik userite sisendid oleksid korralikult escaped, nt SQL ja path traversal eest. Dokumentide üles laadimisel peaks olema limiit suurusel ja peaks jälgima, kas sealt annab kuidagi security perimeetrit rikkuda.

=== Repudiation

Smart-IDga autentitud, kui dokument saadetud. Logifailid vaja hoida turvaliselt. Kui pikalt vaja talletada? Eri asjadel äkki eri pikkus, nt saatmine on tähtis kui mõne staatuse vaatamine. Adminide puhul? Adminide logi/audit failid. Mis siis kui devops nt muudab mingit parameetrit, mis teeb süsteemi ebaturvaliseks? Deployment logi ja branch ruleid, et ei saaks force committida. Eeldame, et välised teenused (TARA, KVKR) järgivad samu põhimõtteid.

kaks võimalust: otse api kaudu info saamine ja in transit info ligipääs. Api kaudu on meil piiritletud delegaatide süsteemiga. In transit suhtes kasutame kliendi vahel HTTPS, teenustega X-teed. Peab jälgima, et stringid on escaped. Iga resurssi requestimisel peab checkima ligipääsu. URLid ei tohi sisaldada a la isikukoodi vmdgi, vaid kasutame suvalisi identifikaatoreid.

=== external services

main data to protect is peoples personal info. Health data is being held by TIS and requested only when a case exists. We send that health data to KVKR.

Should TIS blindly trust our servers and give all data away that we request? We could let the request be signed with the user’s ID-card or Smart-ID and use that signature to get data from TIS. That way even if our servers are compromised, it is harder to get people’s data. Though, we can still get people’s data that have a signed document in our servers. Should it be possible to use the signed document for a limited time only? This depends on the expected length of downtime for TIS.

For KVKR it is probably fine that we can query for any request, as there is not that much info.
